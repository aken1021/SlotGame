# 實作準則

## 規格正規化

保留原始檔。需求記錄包含來源（頁碼/分頁儲存格/段落）、ID、規則、驗收條件及狀態。分清「規格已定」「可逆工程假設」「待確認」「明確允許的 demo」。將多份版本的差異列出，不自行合併互斥規則。

影響結算的必要輸入：盤面尺寸/座標、symbols、reel strips 或取樣模型、paytable、lines/ways/cluster 規則、wild/scatter 優先序、乘倍及四捨五入順序、下注單位、特殊遊戲進出/加局/保留狀態、最大獎與封頂方式。目標 RTP 本身不能推導完整機率模型。

## Server

- 使用精確的最小金額單位或定點數；跨 JSON 的大整數採十進位字串等明確編碼，不依賴浮點金額。
- 數學引擎接受規則版本與受控 RNG 來源。正式亂數與可重現測試來源分離，正式路徑不得開放外部強制盤面或 seed。
- Server 驗證身分、遊戲狀態、下注及餘額；不相信 client 傳來的獎金或免費局數。
- 同一請求 ID 綁定玩家、遊戲及 payload；重送回同結果，ID 相同而內容不同時拒絕。去重記錄與結算持久化；不能只用記憶體 Map 宣稱可跨重啟。
- 寫入回合、遊戲進度與本地帳本需有交易邊界，對同玩家併發給出明確策略。扣款/結果提交後網路中斷，透過回合查詢取回原結果，不重新抽獎。
- 外部錢包無法沿用單一資料庫交易時，記錄請求、狀態、冪等鍵與對帳補償流程；以實際錢包能力為準，不能宣稱天然 exactly-once。
- 恢復資料包含回合/序號、規則版本、模式、剩餘次數、收集/保留盤面及未完成結算；不得將祕密 RNG 狀態暴露給 client。

## 契約

先定義啟動/狀態、spin、特殊遊戲動作、回合查詢及錯誤。這些是語意需求，不預設平台 endpoint 名稱。
明訂：契約版本、玩家識別方式、request/round ID、預期序號、金額編碼、盤面排列、模式、合法動作、wins 與 totalWin 關係、恢復快照。
以至少一份非中獎、一份中獎與每種特殊遊戲回應實例驗證 parser；資料必須由已知規則產生或明確標示為測試 fixture。

## Client

- 輸入、請求中、停輪、報獎、特殊遊戲與恢復分為明確狀態；快速連點不能形成重複下注。
- 畫面消費 server 結果，動態特效不能更改盤面/派彩。允許跳過演出時仍正確結束狀態、顯示 server 總額。
- 超時與斷線先查詢狀態或重送同 request ID，不產生新下注 ID 猜測成功與否。忽略過期回應且能恢復未完成回合。
- Cocos 模式除腳本外需完成 scene/prefab、UUID、property、資產及生命週期綁定；引用存在不等於成功顯示，需實際預覽驗證。
- 演出節奏、音效與資產缺少時記錄缺口；佔位展示與正式美術驗收分開。

# GoldenHen v0.2 複查

依據：2026-10-22 更新的 `GoldenHen_AI規格書.xlsx`，全工作表檢查；未改動原檔，也未透過舊專案補規則。以下「程式已確認」僅代表規格書自己的來源分類，本次沒有重新查驗其引用程式。

## 結論

新版已可支援 client 流程及共用模組設計。補入盤面索引、規則 ID、來源分類、特殊遊戲順序、JP 分支、封包字典、時序與案例，實用性明顯提升。

本次使用者授權可假設金流。因此本機錢包、金額單位、扣派時點、持久化、去重與錯誤處理可由 AI 提出一致方案，不再需要等待外部平台文件。此授權不等同已確認遊戲的抽樣機率、Wild/Scatter 判定、FG 次數或正式賠率。

## 可直接採用的本機金流假設

這些為本次提出的開發假設，不是原公司規則，也未執行實作：

- 使用本機模擬錢包，初始可用額為 1000.00 個測試信用點；不連外部支付。
- 沿用規格已有的顯示比例：1 原始單位 = 0.0001 信用點。Server 用整數儲存；跨 JSON 的金額以十進位字串表示，需相容既有 number 格式時由 adapter 檢查安全整數範圍。
- 顯示保留 2 位小數，使用明訂的十進位四捨五入；顯示取整不回寫帳本。細小派彩可累積，不逐筆因畫面精度而捨去。
- 押注只接受 server 下發的 bet_list 選項。暫不自行假定 total_bet 必定等於 line_bet × 50；二者關係由設定明列。
- 聚寶盆的 1.76/4.4/8.8/17.6/22 門檻按顯示信用點解讀，於比較前轉成原始整數單位；此為本次的明確假設。
- 只在主遊戲合法 spin 扣 total_bet；FG 每局及 JP 選蛋不另扣款。
- 每個 server 動作計算完成後，將該動作新增獎金、結果、遊戲狀態與去重紀錄一起提交。畫面報獎僅延後顯示，不能觸發第二次入帳。total_win_amount 是展示/查詢用累計，不因回傳多次而重複派發。
- 同玩家操作序列化。請求 ID 綁定玩家、動作及 payload；同 ID 同內容重送回原結果，不再抽獎/扣款/派彩；同 ID 異內容拒絕。
- 回應遺失後查詢或重送原請求。重新載入及 server 重啟後以持久化回合與狀態恢復；client 傳來的 balance 只能作診斷，不能作帳務依據。
- 本機 demo 採單一交易式資料庫與錢包 adapter。具體資料庫、API 命名與錯誤碼可由 AI 選擇並記錄。若未來接真實外部錢包，另建立平台 adapter 與對帳規格。

因此 `待補清單!D15`、`封包契約!C45:E45`、`執行環境!A11:D11` 所指的部分平台空缺，已有可行的開發假設，不是本機獨立開發的阻礙。公開部署及公司平台相容仍另行定義。

## 仍影響玩法與結算的問題

### 1. 正式數學仍未提供

位置：`總覽!B9`、`待補清單!D5:D8`、`規則表!H10:H12`。

缺 paytable、抽樣模型/輪帶/權重、機制機率，以及 Wild 的替代集合、純 Wild、最長連線、一般與黃金的混算規則。金流方案只能處理金額保存與移轉，無法唯一決定盤面如何生成。

如果目的先完成可玩的 demo，可以另行明確授權建立「可替換的 demo 數學設定」，並將數值與演算法獨立版本管理；它不能標記成 GoldenHen 的正式數學或正式 RTP。

### 2. FG 末局接 JP 的累計範圍不清

位置：`規則表!E20`、`E22`、`F34`，`FG免費旋轉!B9:B11`。

FG 的 total_win_amount 說包含期間 JP，但末局順序是先顯示 FG 總贏分，再進 JP。需要明訂：末局 JP 是否算 FG 收益？若算，FG 看板如何在 JP 尚未揭曉時呈現？若不算，累計定義要寫出例外。

建議分開定義本局增量、FG 累計、整段主回合累計；逐一標明主遊戲觸發局、FG 中途 JP、FG 末局後 JP 各納入哪個累計，避免漏計或重複顯示。

### 3. FG 的 END 是結果還是額外結束動作？

位置：`規則表!E20:G22`、`E21`、`封包契約!C25:E34`。

需要明確說明末局回應直接為 END 並帶盤面，還是先 PROCESS（剩餘 0）再發下一個請求取 END。最後一局加局時，是先加局再決定 END，還是已結束不能加？同時 retrigger 與 JP 時，局數更新及進場順序也要固定。

### 4. ExtraBet 並未完整定義

位置：`規則表!H5`、`F15`、`F39`、`封包契約!C12:E12`。

原文有 ExtraBet 比例、狀態與選項，卻沒有完整說明它在本遊戲是否實際開啟、提高哪些機率/權益、黃金 state 使用加注前或加注後線注、JP 解鎖是否改變。報獎倍數又特別排除 ExtraBet，需明確定義原始/實付兩種投注基準。

若不需要此功能，直接標「本遊戲停用 ExtraBet」，不要僅因共用封包有欄位而讓 AI 自動實作。

### 5. 黃金門檻格式與非法輸入處理

位置：`規則表!E15:H15`、`黃金圖騰!A2:E8`。

已補演算法，但仍需提供有效五筆範例；第一筆不影響 state 應標為保留值，或在新協定改為四個具名門檻。若沒有任何 i 符合，演算法需明寫預設 state=1。升冪是否嚴格、重複門檻是否允許、資料缺失時是拒絕載入還是使用預設也需定義。

門檻數字可放配置，不需寫死在程式，但要先有一套明確的開發設定。

### 6. JP 壓暗、可中等級與直接 MINI 分支

位置：`規則表!H16`、`H25:H28`、`JP砸金蛋!A2`。

尚未定義壓暗等級是否禁止得獎，以及 state=1 四個都暗時能否觸發 JP。直接 MINI 的進入條件也未決定。這些是玩法規則，不能由錢包設計代替。

另需選定 JP 內容/結果生成模式，固定每顆蛋還是每次選取決定；各等級如何抽樣；多種模式下結束揭示的 18 顆內容須與已揭露歷史一致。

### 7. Scatter 與 FG 輪帶仍無法導出唯一行為

位置：`規則表!H18`、`H21`、`E23:H23`、`驗收案例!D15:G15`。

缺主遊戲進 FG 的確切條件、3/4/5 輪給局數、retrigger 加局與上限。FG 的 fake_wheels 是畫面轉動資料，不能因其中沒有 Scatter 就推斷正式結果不能出現 Scatter；也不能從其中的頻率推算機率。

建議明確分開「視覺假輪帶」與「server 數學輪帶/權重」，並以正式結果規則定義能否加局。

## 契約與案例中的具體不一致

### 8. 用 bingo=[] 判斷沒有獎金，條件不足

位置：`驗收案例!D8:F8`。

目前寫 `bingo=[]` 就期望 `win=0`；如果 Scatter 或其他獎項另有支付，空 ways 明細不保證總獎為零。應改成「bingo=[]、無 Scatter 獎、無其他獎，本局獎金=0」，或限制此案例只測普通 ways。

### 9. 封包還不是可執行契約

位置：`封包契約!C16:E17`、`C22:E26`、`C37:E41`。

需指定採用新舊哪套命令，line_bet/bet_value/BetValue 是別名、同時必填或不同 adapter；serial_id 的型別與用途不能含糊地與金額一起標 number。

JP 恢復用的 -1 表示未開，END 的 -1 表示已開，這可以成立，但必須按狀態分開 schema，避免共用 parser 誤解。補上必填/可無、數值域、完整 request/response 範例與拒絕條件。既有 client 型別 number 與本次 proposed 整數字串金額由 adapter 明確轉換。

Server 不應接受 SPIN 中 balance、dev_mode 等欄位直接改變正式結果。權限與用途由本機共用契約明訂。

### 10. 案例仍依賴未附檔案，且存在遺漏引用

位置：`驗收案例!D11`、`D16:D18`、`D23`、`D27:D28`、`D34:D35`、`規則表!J10`。

多個輸入只有 G63_*.txt 名稱，當前規格資料夾未附這些測試檔，不能不回舊專案就重現。請將固定輸入與完整預期回應放入本案的 fixtures/，或在活頁簿直接列出。

規則表引用 TC-WAY-02～05，驗收表沒有 TC-WAY-05。另 TC-GOLD-02 的「線注等於第 2 門檻即 state=3」應補門檻嚴格遞增等前提，避免重複門檻時期望不成立。

還應增加：FG 末局 retrigger+JP、ExtraBet 切換、非法狀態請求、重送/併發、server 已結算但回應遺失，以及重啟後續局案例。這些可以由 AI 根據定好的共用契約建立。

## 可以由 AI 完成、無需再要求補齊的工程項

- 本機 server 語言、資料庫、啟動方式與 API 命名：在無公司相容限制時可選擇並記錄。
- 共用通訊、去重、回合保存、錢包與恢復：採前述本機假設設計。
- 類別分層與擴充點：可從遊戲差異抽出，不必由企劃先寫完整介面。
- 非結算時序：`演出時序!A2` 已允許 AI 決定並記錄，可直接完成 demo 預設。
- 尚未交付的美術：可以先用佔位圖或依授權製作，但正式外觀相符仍需參考圖及資產驗收。

Cocos 的轉速 35 尚未給獨立單位或位移公式（`演出時序!B6:D6`），故無法只靠數字重現舊框架手感；可作為允許 AI 提案的演出參數，或補每秒移動格數。核心玩法開發無須因此停下。

## 建議下一次修改方式

不必再增加大量程式路徑。優先把尚未定案的玩法規則變成可選決策，填入正式選擇；將數學/測試附件一起交付。

本書可增加一段「本機獨立開發授權」：金流與一般工程方案由 AI 決定並記錄、非結算演出採 demo 預設、正式數學與玩法以已核定規則為準。新指示已授權的金流項目不應再被「待平台確認」的舊標籤擋住。

目前可開始寫共用框架與 client 流程；要產出結果可重現的完整 GoldenHen，仍先解決數學、FG/JP 邊界、ExtraBet、黃金門檻與案例附件。

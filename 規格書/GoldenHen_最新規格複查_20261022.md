## 真正仍需規則決策的四組內容

### A. 數學模型與計獎方式

位置：`待決事項!C5:H10`，對應 Q-01～Q-06。

仍缺正式 paytable、結果抽樣/權重/輪帶、機制機率，以及 ways 分筆與最長連線、Wild 替代和共用、一般/黃金混算、Scatter 觸發/支付、FG 初始次數/加局/上限。

這些不是 server 語言或錢包問題。Client 需要哪些資料能確定「server 回傳格式」，無法唯一決定「盤面應如何生成與派彩」。例如 client 同時能顯示 Wild 替代或不替代 Scatter，代表兩個規則皆可呈現，不能因此判定哪個是正式玩法。

可選處理方式：提供正式數學附件，或明確授權 AI 決定一套可替換的 demo 數學/玩法設定。後者可產出可玩的完整開發版，但不能標記為正式 GoldenHen 機率或 RTP。規格本身目前仍禁止採用測試賠率。

### B. 黃金門檻與轉換

位置：`規則表!E16:H17`、`黃金圖騰!A2:E8`、`待決事項!C12:H12`。

需要一套有效門檻與其單位，以及抽樣前/後轉換政策。Client 需要五筆升冪，D01/D02 卻是四筆降冪，不能只反轉陣列後當正式值使用。

AI 可補的工程細節：明定未達任何門檻時 state=1；缺欄位或非法門檻啟動失敗；新契約可使用四個具名解鎖門檻，由舊格式 adapter 補保留列。實際解鎖值與混算行為仍需依核定規則配置。

### C. JP 得獎資格、直接 MINI 與開獎方式

位置：`待決事項!C13:H15`，Q-08～Q-10。

仍需決定：壓暗是否禁止得獎、state=1 可否觸發、何時直接 MINI、觸發的判定單位/機率、獎金模式、選蛋是固定內容揭露或逐次產生。這些不能從四個 UI 欄位反推出。

金額可配置及本機支付都能由 AI 完成，但「哪種等級能開出」「點選是否影響結果」是玩法決策，需有明確答案或 demo 授權。

### D. 美術交付與正式畫面驗收

位置：`待決事項!C18:H18`、`美術風格!C10`、`UI圖素!A2`。

仍無畫面參考圖、已交付資產清單、pivot/anchor、動畫格式及事件資料。本活頁簿沒有嵌入圖片。可先用佔位資產或授權製作新資產，足以實作功能；重現舊遊戲的外觀及演出則仍需驗收依據。

## 這次查出的資料與規格矛盾

### 1. D07-1 的 Scatter 標記與盤面不符

位置：`測試資料!E68`、`待決事項!E9`。

可視輪 0=[23,2,24]、輪 1=[17,1,19]、輪 2=[15,2,20]。第 2 輪中間是 Wild（ID 1），但 win_special_symbols 將前三輪中間全部標為 1。待決事項又描述 D07-1 為前三輪各一個 Scatter。

若 Wild 可代替 Scatter，這可能是刻意標記替代位置；但這正是 Q-03 尚未決定的規則。故不能拿此資料證明「前三輪都是 Scatter」或正式觸發條件。

處理：保留為歷史流程 fixture；另依核定規則產生盤面、標記與觸發一致的 fixture。

### 2. FG 加局後總次數倒退

位置：`測試資料!E73:E75`。

D07-6、D07-7 的 sg_map["1"]=6，但 D07-8 END 又回 4。與「總次數含加局」的定義不一致，可能使末局次數條與統計錯誤。不是金額問題，即使只驗畫面流程也要隔離此異常。

處理：生成新的自洽序列，完成前不允許總次數無規則地降低；原始列標示不作計數正確性的驗收來源。

### 3. D02 投注表違反排序與金額型別

位置：`測試資料!E7`、`規則表!E5`、`E48`。

D02 的 total_bet 從 0.5 增加至 350，是升冪，不是規格要求的降冪；line_bet 等欄位有小數，也不符合本機整數原始單位。此列另缺 current_line_bet，故不是完整的正式 START_GAME 範例。

處理：另建開發環境有效配置，先指定原資料單位再做精確縮放，按降冪輸出並補齊當前押注。不要只對小數取整或直接放進 Go int64，否則小注可能變成 0。若有需要，保留 legacy adapter。

### 4. JP 金額欄位缺漏，非終局支付語意不明

位置：`封包契約!E43`、`規則表!E31:E32`、`E51`、`測試資料!E88:E91`、`E96:E104`。

規格要求 JP PROCESS/END 都帶 sg_map["6"]，但內嵌 JP 回應缺少它；普通點選也沒有 this_win_amount/total_win_amount。必須補有效的新 fixture，不能以缺欄位的舊資料驗證新 server。

可由 Go 契約補齊的保守實作：未集滿時本次結算增量=0，當回應實際完成得獎才支付一次；sg_map["6"] 明確區分尚未定獎的 0 與已定獎的金額。若設計需提前顯示獎金，使用展示金額，不將展示值重複入帳。這是候選實作方案，並非本次已核定遊戲數學。

### 5. 錢包驗收公式漏了押注或基準時點

位置：`驗收案例!D43:F43`。

TC-WAL-05 寫「結束後餘額 = 觸發前餘額 + 整段 total_win_amount」。若觸發前指送 SPIN 之前，則漏扣 total_bet；若指已完成觸發局扣派後，則要說明 total_win_amount 是否排除已入帳的主遊戲獎。

建議使用可核對的整段公式：以主遊戲 SPIN 前餘額 B0 為基準，最終餘額 = B0 − total_bet + 主遊戲獎 + 所有 FG 局獎 + 各次 JP 獎，每個項目只計一次。演出累計欄位不得再次入帳。

### 6. JP 先於 FG 時的總獎範圍要寫清楚

位置：`規則表!E27`、`E36:F36`、`測試資料!E116:E121`。

FG-007 提到包含 FG 期間 JP，但 D12 先完成 JP 再進 FG，後續 FG total_win_amount 仍包含先前 JP（D12-8 已為 6985201；最終為 7001201）。

依 client 現有累計資料，可將 total_win_amount 定義為「同一段特殊遊戲鏈的累計」，包括 JP→FG、FG→JP→FG。FG 看板若直接讀此欄位，就不一定只代表 FG 自身收益。若希望純 FG 收益，要另設欄位，不能換一個名稱卻混用數值。

### 7. 假輪帶不是數學輪帶

位置：`待決事項!C10`、`規則表!E25:H25`、`封包契約!E5`。

原文「不含 Scatter 則不可能加局」只有在指正式結果取樣資料時才成立；fake_wheels 是轉動視覺資料，不含 Scatter 不能單獨證明 server 結果不含 Scatter。

建議兩種資料使用不同名稱與說明，避免 AI 把假輪帶拿去當正式抽樣權重。

## 可直接由 AI 完成、不必再列為待補的項目

- Q-13 的 server 語言：已確定 Go，舊「待平台確認」標籤已被本次使用者指示取代。
- HTTP/其他本機傳輸、錯誤碼、request/round ID、狀態序號、同玩家併發政策：由 AI 定義正式契約並讓新 client 共用；不要求企劃指定內部實作。
- Go 的金額採整數型別並做安全範圍檢查；既有 client 解析 number 時，確保不超出 JS 安全整數，否則採字串與 adapter。
- 新舊命令別名、required/optional、JP 不同狀態的 -1 含義：依已知欄位做狀態分型，不需要使用者另寫 Go 結構。
- 主遊戲 win_type 可先以現有 WinType 門檻建立一致的可配置開發預設；明列這是演出分級，不改變派彩。
- 本機假錢包與 WAL 規則可以開始做，不等待正式平台文件。
- 非結算秒數已有 AI 決定的授權，不作功能開發阻礙。
- 欠缺末局 JP/加局+JP 的 fixture，可依已寫明的流程產生，不必要求取回舊程式才可開發。
